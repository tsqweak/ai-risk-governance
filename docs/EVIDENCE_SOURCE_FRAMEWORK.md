# Evidence Source Framework

Platform: AI-Risk-Governance
Purpose: AI Governance Operations blueprint

## Purpose

The AI-Risk-Governance platform now explains what governance exists across AI systems, regulations, controls, evidence, monitoring, risk, lifecycle, agentic authority, and auditor workflows.

The next operating question is:

```text
Where does the evidence come from?
```

This document explains how AI governance evidence originates, how it is collected, how it is validated, and how much of it can be automated. It is intended for the AI Governance Working Group, IT Risk, Internal Audit, Compliance, and technology leaders who need to move from governance design to governance operations.

For every governance control, the operating model should answer:

- What evidence is required?
- Where does that evidence come from?
- How is it collected?
- How is it validated?
- Can it be automated?

## 1. Governance Evidence Model

The evidence source model is:

```text
Control
  -> Evidence Requirement
  -> Evidence Source
  -> Collection Method
  -> Validation Method
  -> Evidence Object
  -> Monitoring
```

### Control

A control defines the governance expectation. It states what must be true for the AI system to be governed, compliant, monitored, or approved.

Example: `AI-GOV-006 Tool Permissions Approved`

### Evidence Requirement

An evidence requirement defines what proof is needed to support the control.

Example: Approved tool permission register, denied tool rationale, access review record.

### Evidence Source

An evidence source is the system, repository, workflow, log, record, file, or human decision where proof originates.

Example: Tool policy file, permissions table, access management system, approval workflow.

### Collection Method

The collection method explains how the platform obtains the evidence.

Examples:

- API pull from a source system.
- Repository scan.
- Runtime log ingestion.
- Manual upload.
- Governance workflow capture.
- Generated report.

### Validation Method

The validation method explains how the platform determines whether evidence is valid.

Examples:

- Schema validation.
- Approval status check.
- Expiration check.
- Owner/reviewer match.
- Control test result.
- Cross-check against regulatory mapping.
- Internal Audit review.

### Evidence Object

An evidence object is the governed record retained by the platform. It has an ID, title, type, owner, reviewer, status, version, source, approval date, expiration date, and linked governance objects.

### Monitoring

Monitoring checks whether required evidence exists, remains current, is approved, is valid, and continues to support the control.

This model matters because governance cannot rely on status alone. A dashboard status is only credible when the platform can show the proof behind it, where that proof came from, who reviewed it, and how it is monitored.

## 2. Evidence Categories

### System Generated Evidence

System generated evidence originates directly from systems, repositories, runtime platforms, configuration stores, or logs.

Examples:

- Logs
- Prompt versions
- Model versions
- Tool policies
- Monitoring results
- Runtime activity
- Execution logs
- Kill switch status
- Access control records
- Configuration files

System generated evidence usually has the highest automation potential because the source can often be queried, scanned, or ingested.

### Derived Evidence

Derived evidence is generated by analyzing, summarizing, or packaging other evidence and governance records.

Examples:

- Risk reports
- Control reports
- Coverage reports
- Evidence health reports
- Audit packages
- Regulatory traceability reports
- Control implementation coverage reports

Derived evidence can often be automated after the underlying source evidence is reliable. Its trust depends on traceability back to source records.

### Human Governance Evidence

Human governance evidence originates from accountable decisions, approvals, acceptances, committee actions, and management judgment.

Examples:

- Risk acceptance
- Exception approval
- Production approval
- Pilot approval
- Governance committee decisions
- Model validation sign-off
- Human oversight procedure approval
- Delegated authority approval

Some evidence can never be fully automated because governance includes judgment. A system can collect the approval, route the workflow, check whether the approval exists, validate approver authority, and monitor expiration. It cannot fully automate the accountability decision itself.

## 9. Automation Assessment

### Travel Brain

Estimated evidence mix:

- Automatically Collected: 45%
- Derived: 30%
- Human Generated: 25%

Rationale:

Travel Brain is recommendation-oriented and has bounded authority. Its prompt records, model records, tool permissions, monitoring results, evidence health, and traceability reports can be substantially automated. Risk assessments, oversight procedures, and production approval still require human governance decisions. Derived evidence such as audit packages, regulatory coverage reports, and evidence health summaries can be generated from platform records once sources are integrated.

### Autonomous Payment Agent

Estimated evidence mix:

- Automatically Collected: 55%
- Derived: 20%
- Human Generated: 25%

Rationale:

Autonomous Payment Agent has more runtime evidence because tools, actions, execution logs, transaction limits, approval references, and kill switch state can be collected from technical systems. However, high-impact authority decisions, production approval, risk acceptance, and exception approval still require human accountability. Derived evidence remains important, but runtime logs and configuration evidence become a larger share of the assurance model.

## 10. Future Platform Implications

To evolve from governance documentation to governance operations, the platform should add integrations and workflows that collect evidence at the source.

### Git Integration

Purpose: Collect policy files, prompt versions, architecture diagrams, configuration, control tests, and implementation evidence from repositories.

Operational impact: Evidence can be tied to commit history, owner, reviewer, and version.

### Prompt Repository Integration

Purpose: Collect prompt versions, approval status, prompt owner, change history, and test results.

Operational impact: Prompt governance moves from manual attestations to inspectable version history.

### Model Registry Integration

Purpose: Collect model version, provider, deployment metadata, validation status, fallback model, and lifecycle state.

Operational impact: Model inventory and validation evidence can be verified against deployed reality.

### Policy File Collection

Purpose: Collect tool policies, agent policies, transaction limits, denied tools, approval thresholds, and kill switch configuration.

Operational impact: Governance engineering can validate that controls exist as technical implementation.

### Runtime Log Collection

Purpose: Collect tool calls, actions, execution outcomes, approval references, runtime errors, and kill switch events.

Operational impact: Agentic governance can prove what the agent actually did, not only what it was allowed to do.

### Approval Workflow Collection

Purpose: Collect risk acceptance, exception approval, production approval, model validation approval, and committee decisions.

Operational impact: Human governance evidence becomes structured, reviewable, and expiration-aware.

### Evidence Validation Automation

Purpose: Validate schema, required fields, owner, reviewer, approval status, version, source, expiration, and linkage to controls or regulations.

Operational impact: Evidence quality can be monitored continuously.

### Evidence Freshness Monitoring

Purpose: Detect stale, expired, missing, unapproved, or invalid evidence.

Operational impact: Evidence becomes an operational control with findings and exceptions rather than a static artifact.

## Recommendations for Future Platform Development

1. Add an Evidence Source Registry.

Each evidence requirement should identify a source system, source owner, collection method, validation method, and automation level.

2. Add Evidence Collection Jobs.

The platform should support scheduled jobs for Git, prompt registry, model registry, policy repository, runtime logs, and approval workflow collection.

3. Add Evidence Validation Rules.

Each evidence type should have validation rules: required metadata, accepted source, freshness threshold, approval requirement, and linkage requirement.

4. Add Source-to-Control Traceability.

Auditors should be able to inspect a control and see not only evidence objects, but the source systems and collection history behind those evidence objects.

5. Add Human Decision Workflows.

Risk acceptance, exception approval, production approval, delegated authority changes, and governance committee decisions should be captured in structured workflows rather than uploaded as static files.

6. Add Runtime Assurance for Agentic AI.

Agentic systems need runtime log ingestion, approval-reference validation, tool-policy validation, kill-switch test validation, and execution-limit monitoring.

7. Add Evidence Automation Metrics.

Dashboards should show how much evidence is automatically collected, derived, or human generated by system, control domain, and regulator.

8. Preserve Human Accountability.

The platform should automate collection and validation wherever possible, but it should not imply that governance judgment can be fully automated. Human approvals, risk acceptances, committee decisions, and oversight judgments remain accountable governance acts.

## Closing View

The bridge from governance documentation to governance operations is evidence sourcing.

```text
Governance documentation says what should be true.
Governance assurance shows proof.
Governance operations collects and validates proof at the source.
```

The AI-Risk-Governance platform should continue evolving toward source-connected evidence collection so that every major governance object can answer:

```text
Show me the proof.
Where did it come from?
Who reviewed it?
How was it validated?
Is it still current?
```
